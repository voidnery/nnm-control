# Эпоха `1:` и переход клиентов на DIST-Control — варианты

Дата: 2026-10-24. Основание: D-0012 шаг 2, R-0001.2 §11, поручение T-0012 п.4. **Документ — анализ для
решения оператора. Переход не реализован**: пакет и скрипты ниже — предложение, клиенты не тронуты.

## 1. Исходные факты

| # | Факт | Источник |
|---|---|---|
| F1 | Установленные клиенты держат `nnm-control` версии `1:<X.Y.Z>` (последняя — `1:1.31.1`) из APT на GitHub Pages `https://voidnery.github.io/nnm-control/apt`; стек — образы `ghcr.io/voidnery/nnm-control-{api,web}:<X.Y.Z>` | `.github/workflows/legacy-apt.yml`, `packaging/build-deb.sh` |
| F2 | Эпоха введена в 0.59.0, чтобы схема 0.x встала выше случайного `1.8.5` (без эпохи) в пуле Pages; с тех пор все выпуски — `1:`, а нумерация продолжена с 1.8.6. | F3 | Для dpkg любая версия без эпохи ниже любой `1:…`: `2.0.0` < `1:0.0.1` | Debian Policy §5.6.12 |

| F5 | ERS/1 §4 запрещает эпохи; `eterix-ci/scripts/check-deb.sh` отклоняет пакет с эпохой | `eterix-contracts/ers-1.md` §4; `check-deb.sh:23` |
| F6 | DIST-Control эпоху поддерживает (имя файла без неё), но **не примет версию ниже наибольшей в пуле продукта**: если в пуле `nnm-control` лежит `1:1.31.1`, ingest `2.0.0` получит отказ «the pool already has 1:1.31.1» | `dist-control/apps/api/src/lib/publish.js:441-451` |
| F7 | По документам прежнего штаба на origin DIST-Control опубликован stable `1:1.31.1`; кто его ставил — неизвестно | HANDOFF T-0012 (гипотеза — пул на узле не проверен) |
| F8 | apt берёт кандидатом **наибольшую** версию из всех источников: пока у клиента подключён старый APT с `1:…`, `apt upgrade` вернёт его на версию с эпохой, даже если стоит `2.0.0` | поведение apt (`apt-cache policy`) |
| F9 | Тонкий пакет этой ветки (`build.sh`) — без эпохи, `Package: nnm-control`, и совместим со старым по данным: тот же проект compose, тома `mongo_data`/`media_spool`/`geoip_db`, `/etc/nnm-control/nnm-control.env` (JWT_SECRET — ключ зашифрованных полей), те же вопросы debconf и пути файлов | `packaging/eterix/`, `backend/tests/eterix-package.test.mjs` |
| F10 | preinst тонкого пакета при замене `1:…` видит **понижение** и снимок не снимает (R1) — снимок для перехода надо снять заранее (`nnm-control backup` есть в старом пакете) | `packaging/eterix/debian/preinst` |

Вывод из F3–F6: **пакет без эпохи не может «обновить» клиента с эпохой обычным `apt upgrade`, а движок не
может обслуживать продукт с эпохой.** Любой путь требует либо изменения движка и контрактов, либо
одного необычного шага на каждом клиенте.

## 2. Варианты

### A. Эпоха `1:` навсегда — меняем контракт и движок

- **Клиент:** ставит `eterix-keyring` и `eterix-updater`, подключает источник DIST-Control
  (инсталлятор DIST-Control), отключает старый APT; дальше `apt upgrade` → `1:2.0.0` — обычное
  обновление, без понижения.
- **Работа:**
  - eterix-updater (класс A): шаблон версии с необязательной эпохой, сравнение с эпохой первой,
    `Upstream` без эпохи для `/healthz`, тест против dpkg, повторное доказательство защит диверсиями,
    полевой прогон `VERIFIED` — 1–2 поручения;
  - eterix-contracts: upd/0 §5.6 (E2), ERS/1 §4 — исключение для `nnm-control`;
  - eterix-ci: параметр `check-deb` «эпоха разрешена» для одного продукта;
  - nnm-control: версия `1:X.Y.Z` в `build.sh`; preinst — снимок без хука, когда заменяется пакет
    старого пути (у него хуков нет — сейчас preinst в этом случае откажет).
- **Риски:** исключение навсегда в доверенном движке ради одного продукта; каждая будущая проверка
  версий во всех продуктах должна помнить об эпохе; ручной шаг со сменой источника всё равно остаётся.

### B. 2.0.0 без эпохи + разовая ручная миграция (рекомендуется)

- **Клиент (один раз, по инструкции или скриптом):**
  1. снимок: `sudo nnm-control backup` (старый пакет; на этом пути preinst снимок не снимет — F10);
  2. подключить Eterix: `eterix-keyring`, источник DIST-Control `/etc/apt/sources.list.d/eterix-nnm-control.sources`
     и канал (инсталлятор DIST-Control);
  3. **удалить источник старого APT** (иначе F8 вернёт версию с эпохой);
  4. `sudo apt-get update && sudo apt-get install --allow-downgrades nnm-control=2.0.0` — dpkg
     считает это понижением, apt требует флаг; заодно ставится `eterix-updater` (Depends);
  5. проверка: `curl -s http://127.0.0.1:8580/healthz` → `"version":"2.0.0"`; данные на месте
     (тома и `nnm-control.env` те же — F9).
  Дальше обновления — движком, без ручных шагов.
- **Работа:**
  - nnm-control: скрипт миграции (шаги 1–5 с проверками и откатом на старый пакет при провале),
    прогон на ВМ со старым `1:1.31.1` → `2.0.0`, раздел README — S–M;
  - DIST-Control: убрать `1:1.31.1` из пула и индексов продукта `nnm-control`, если он там есть (F6/F7);
    штатного «удалить из пула» в 0.59.x нет (есть только repair индекса канала) — вручную на узле или
    маленькая доработка;
  - eterix-updater, eterix-contracts, eterix-ci — **без изменений** (ERS/1 §4 соблюдён).
- **Риски:** ручной шаг на каждом клиенте; клиенты, о которых оператор не знает, останутся на
  `1:1.31.x` (MIT, работает как есть) — это совпадает с закрытием продукта; `--allow-downgrades`
  требует аккуратной инструкции; пока старый APT включён у клиента — F8.

### C. Переходный пакет в старом APT (`1:1.99.0`)

- **Идея:** последний выпуск старого пути, который сам готовит переход: снимок, файл источника
  DIST-Control, ключ origin, apt-pin `Pin-Priority: 1001` на `nnm-control` из DIST-Control — со
  следующим `apt upgrade` apt сам «понизит» пакет до `2.0.0`.
- **Клиент:** два `apt upgrade` без ручных шагов.
- **Работа:** переходный пакет и его e2e (M); ключ origin в пакете продукта — дубль `eterix-keyring`;
  доступ клиента к DIST-Control: для закрытого продукта нужны учётные данные клиента, которых
  переходный пакет не знает.
- **Риски:** pin `>1000` разрешает понижения вообще — ошибка в пине откатит пакет; продукт меняет
  доверие apt на хосте без явного согласия администратора; для неизвестных клиентов не работает,
  если раздача в DIST-Control закрытая.

### D. Переименовать пакет (новый slug) — без эпохи и без понижения

- **Идея:** классическое переименование Debian: новый пакет (например, slug `nnm`), а последний
  `nnm-control 1:1.99.0` — пустой переходный с `Depends:` на новый; новый — `Replaces/Breaks:
  nnm-control (<< 1:1.99.0)`.
- **Работа:** ERS/1 §1 (реестр slug), продукт и токены в DIST-Control, каталоги движка, документы —
  смена slug выпущенного продукта (upd-desc/0 §2: «смена продукта для движка»); клиенту всё равно
  нужен источник DIST-Control.
- **Риски:** большой объём ради одного шага; имя `nnm-control` уходит из реестра.

## 3. Сравнение

| | A — эпоха навсегда | **B — 2.0.0 + ручная миграция** | C — переходный пакет | D — новый slug |
|---|---|---|---|---|
| Шаги клиента | смена источника | смена источника + `--allow-downgrades` | два `apt upgrade` | смена источника |
| eterix-updater | меняется (класс A) | нет | нет | нет |
| eterix-contracts | upd/0 E2, ERS/1 §4 | нет | нет (по желанию — заметка) | ERS/1 §1 |
| eterix-ci | `check-deb` | нет | нет | нет |
| DIST-Control | нет | убрать `1:1.31.1` из пула | убрать `1:1.31.1` из пула | новый продукт |
| nnm-control | версия с эпохой, preinst без хука | скрипт миграции + ВМ-прогон | переходный пакет + e2e | переименование |
| Главный риск | исключение в доверенном движке навсегда | ручной шаг, флаг понижения | pin > 1000, доверие apt | объём, смена продукта |

## 4. Рекомендация

**B — выпустить закрытую версию как `2.0.0` без эпохи и перевести известных клиентов разовой
миграцией по скрипту.** Это единственный вариант без изменений в движке класса A и в контрактах всех
продуктов; совпадает с D-0012 (закрытие — со следующей мажорной версии); ручной шаг делается один раз
и только там, где оператор знает клиента. Неизвестные клиенты остаются на MIT-версиях `1:1.31.x`,
которые им уже принадлежат (N-0011 оговорка 1).

Порядок, если оператор выберет B:
1. Проверить пул продукта `nnm-control` на origin DIST-Control; если там `1:1.31.1` — убрать из
   пула и индексов каналов (F6). Без этого ingest `2.0.0` откажет.
2. Отдельным поручением: скрипт миграции и его прогон на ВМ `1:1.31.1` → `2.0.0`
   (данные, `nnm-control.env`, health, отсутствие старого источника после миграции).
3. Выпуск `2.0.0` (VERSION, оба `package.json`, раздел CHANGELOG, проприетарная LICENSE —
   `docs/LICENSE-2.0-draft.txt`) → beta → 72 ч → stable.
4. Миграция известных клиентов; затем выключить старый путь: `legacy-apt.yml`, ветка `gh-pages`,
   Pages, образы GHCR (шапка `legacy-apt.yml`).

## 5. Что решить оператору

- Вариант (A / **B** / C / D).
- Есть ли `1:1.31.1` в пуле `nnm-control` на origin DIST-Control и кто его ставил (F7).
- Список известных установок (в том числе собственных) для миграции.
- Будет ли раздача `nnm-control` в DIST-Control открытой (Free без учётных данных) или по токенам —
  от этого зависит, может ли вообще неизвестный клиент перейти (вариант C).
